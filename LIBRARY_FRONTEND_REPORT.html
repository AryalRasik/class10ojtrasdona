Abstract

The frontend of the Library Management System (LMS) is the complete user-facing interface of the digital library platform for Shree Saraswati Secondary School. It is implemented as a Single Page Application (SPA) using pure HTML5, CSS3, and vanilla JavaScript — deliberately without heavyweight frameworks like React or Angular — to keep the application fast, easy to maintain, and understandable for school-level developers.

A custom hash-based router manages navigation across more than 30 pages organised into four groups: catalog pages (browse, book detail, categories, new arrivals, top rated), community and information pages (announcements, events, calendar, rules, FAQ, support, help, feedback), member pages (login, profile, my books, borrow history, notifications, settings), and a full admin panel with eight management screens for books, users, reports, settings, audit logs, import, study materials, and dashboard. Every page is an independent module exposing a render() method, giving the codebase a clean and testable structure.

The interface is designed for a broad audience of students and staff. It features dark and light themes driven by CSS custom properties, a fully responsive layout with a desktop sidebar, a mobile bottom navigation bar, and a floating action button, plus a custom component library — toast notifications, modal dialogs, star ratings, book covers, QR codes, and barcodes — all built from scratch without any external CSS or JS frameworks.

The frontend also behaves as a Progressive Web App (PWA). A service worker caches the application shell and fonts using a network-first strategy so the library remains usable offline, and a web app manifest lets students install the app on their phones. The backend is powered by Supabase, a cloud-hosted PostgreSQL database with authentication and row-level security. The application is deployed as a static site on Vercel, and the source is organized into clear layers (router, state, API, utilities, components, pages) that have been tested across multiple browsers and device sizes.

Keywords: Frontend, Single Page Application, Vanilla JavaScript, HTML5, CSS3, Hash Router, Responsive Design, Dark Mode, PWA, Service Worker, Supabase, Progressive Web App

1. Introduction

1.1 Outline of the Project

The Library Management System project, built using vanilla HTML5, CSS3, and JavaScript, includes several essential components. Initially, the project outlines the background of the educational sector, defines its objectives, and sets its scope. The system will feature user authentication (Admin, Teacher, Librarian, and Student), book cataloging, borrow request management, digital library access, and administrative reporting. HTML5 will be used for structuring the web interface, CSS3 for styling and theming, and vanilla JavaScript for all application logic including routing, state management, and API communication, with data stored in a centralized Supabase PostgreSQL database.

The design phase covers the creation of an intuitive user interface using CSS custom properties for theming and the establishment of a custom hash-based SPA router. During implementation, the project involves coding the frontend components, integrating the Supabase backend logic, and thorough testing to ensure data accuracy and reliability. After deployment, the system will require ongoing maintenance and support to handle growing institutional data. The project concludes with an evaluation of its performance, collection of user feedback, and recommendations for future enhancements to improve the system's effectiveness and user satisfaction.

1.2 Objectives

The main objectives of the frontend development are as follows:

  • To build a responsive and accessible Single Page Application (SPA) for Shree Saraswati Secondary School's library that works seamlessly on desktop, tablet, and mobile devices.
  • To implement a custom hash-based client-side router in approximately 130 lines, supporting parameterised routes (e.g., /book/:id), route guards, and page transition animations.
  • To implement role-based navigation so each user (Student, Teacher, Librarian, Admin) sees only the menus and pages relevant to their role.
  • To develop a searchable book catalog containing 100+ CDC curriculum textbooks with advanced filtering by category, grade, subject, author, publisher, language, and availability.
  • To develop a complete book borrowing lifecycle management system including request, approval, pickup, return, renewal, and fine calculation — all from the frontend.
  • To provide a digital library section for accessing PDF textbooks and study materials online.
  • To implement a notification system for timely communication of library events, due dates, and announcements.
  • To build an admin dashboard with borrowing reports, usage statistics, and audit trail logging.
  • To deploy the system as a Progressive Web App (PWA) for mobile installability and offline support via service worker caching.
  • To support light/dark themes and smooth transitions for a polished user experience.
  • To keep the codebase simple and modular enough that it can be maintained, extended, and studied by school students.

1.3 Advantages

The Library Management System offers several advantages for both school administration and users such as students, teachers, and librarians. Here are the key benefits:

  1. Time Saving: Instant book search and digital borrowing eliminates the need for physical browsing, saving time for both students and librarians.
  2. Easy Data Management: Stores all book, student, and borrow records in a centralized cloud database, making data easy to access, search, and update.
  3. Accuracy and Reliability: Automated fine calculation, due date tracking, and status updates eliminate human errors in manual record-keeping.

  7. Modern Technology Use: Built using vanilla JavaScript, HTML5, CSS3, and Supabase, providing a fast, responsive, and user-friendly interface.
  8. Offline Support: PWA capabilities with service worker caching allow basic access even without internet connection.
  9. Zero Hosting Cost: Because the frontend is static, it deploys free on Vercel with CDN-level speed worldwide.

2.1 Vanilla JavaScript & HTML5/CSS3

Unlike the School Management System built with React and Next.js, this project deliberately avoids framework dependencies. All pages are plain JavaScript objects with a render() method that returns HTML strings. This means no build step, no webpack, no npm scripts for the frontend — just open index.html in a browser. Every component is readable by a Grade 10 student who knows basic JavaScript. The entire frontend is about 35 JavaScript source files totaling roughly 8,000 lines.

2.2 Supabase (PostgreSQL + Authentication)

Supabase provides the backend infrastructure: a PostgreSQL database with 24 interrelated tables, authentication with JWT tokens, and Row Level Security (RLS) policies that enforce role-based access. The frontend communicates with Supabase through the JavaScript SDK loaded from vendor/supabase.js. All database operations — querying books, creating borrow requests, fetching notifications — happen client-side through the SDK, which means no custom backend API is required for production.

async createAnnouncement() {

                content: newAnnouncement.content,

        newAnnouncement.id = Date.now();

    this.showCreateForm = false;
    const container = document.getElementById('pageContent');
    if (container) {
        container.innerHTML = this.render();
        Router.bindLinks();
        Router.highlightNav();
    }

async signUp() {
    const { name, email, password, role } = this;   // role: student | teacher
    const userId = 'U' + Date.now();

    if (AppState.isSupabaseConnected) {
      // Real backend: Supabase Auth + auto profile via trigger

      this.setMode('signin');
    }
}

5. Component Architecture & State Management

5.1 Modular Page Architecture

Every page is a plain object registered with the router in app.js. This "component-first" pattern keeps concerns separated — a page describes its own HTML, its own events, and nothing else. The architecture has four layers:

  • Router (router.js) — matches #/path against registered routes, resolves dynamic parameters (e.g. /book/:id), runs beforeNavigate guards, renders the page into #pageContent, and rebinds navigation links.
  • State (state.js) — a singleton AppState holding the session and all domain collections; loads data in parallel via Promise.all after sign-in, and falls back to a localStorage-powered demo mode when the network is unreachable.
  • Data access (api.js) — a single seam to Supabase that maps database rows to the camelCase objects used by pages.
  • Utilities (utils.js) — shared helpers: HTML escaping, date and currency formatting, debounce, library open-hours detection, star-rating generation, and the SVG icon dictionary of over 50 icons.
js/router.js — real router (excerpt)
const Router = {
  routes: [],
  beforeNavigate(callback) { this._beforeNavigateCallbacks.push(callback); },

  init() {
    window.addEventListener('hashchange', () => this.resolve());
    this.resolve();
  },

  resolve() {
    const hash = window.location.hash || '#/';
    const full = hash.substring(1);
    const [pathPart, queryPart] = full.split('?');
    const query = {};
    if (queryPart) new URLSearchParams(queryPart).forEach((v, k) => { query[k] = v; });

    let matched = null, params = { ...query };
    for (const route of this.routes) {          // match /book/:id style routes
      const routeSegs = route.path.split('/');
      const pathSegs = pathPart.split('/');
      if (routeSegs.length !== pathSegs.length) continue;
      let ok = true; const p = { ...query };
      for (let i = 0; i < routeSegs.length; i++) {
        if (routeSegs[i].startsWith(':')) p[routeSegs[i].slice(1)] = decodeURIComponent(pathSegs[i]);
        else if (routeSegs[i] !== pathSegs[i]) { ok = false; break; }
      }
      if (ok) { matched = route; params = p; break; }
    }
    if (!matched) matched = { handler: this._notFound };   // 404 page
    return this.render(matched.handler, params);
  },

  async render(handler, params) {
    const container = document.getElementById('pageContent');
    const html = await handler.render(params);
    container.innerHTML = html;
    if (handler.afterRender) await handler.afterRender(params);
    this.bindLinks();      // one listener per [data-nav] link

5.3 Global State (state.js)

On sign-in, the API layer fetches books, categories, borrow requests, reservations, notifications, favorites, reviews, digital books, and study materials in parallel and stores them in AppState. Pages read this single source of truth and call api.js for writes; a small confirmation helper and toast system report success. This one-way flow — action, API call, state refresh, re-render — keeps the application predictable and easy to debug.

The AppState singleton (1,778 lines) maintains data collections (books, categories, borrowRequests, reservations, favorites, notifications, announcements, events, digitalBooks, studyMaterials, auditLogs, activityLogs, feedback, calendarEvents, faqs, contactMessages, bookImports), a role system with 4 roles and ROLE_PERMISSIONS/ROLE_CONFIG, core business logic (canBorrow(), canReserve(), canRenew(), createBorrowRequest(), approveBorrowRequest(), processReturn(), renewBorrow(), reserveBook()), and a dual backend with Supabase (production) and localStorage demo mode fallback.

5.4 API Layer (api.js)

api.js wraps every Supabase database operation into simple async functions (Api.getBooks(), Api.createBorrowRequest(), etc.) that map snake_case database columns to camelCase JavaScript objects. When Supabase is unreachable, the API layer transparently falls back to localStorage, making the application fully functional even without a network connection.

7. PWA & Deployment

7.1 Service Worker (sw.js)

The service worker caches the application shell (HTML, CSS, JS, images) at install time under a versioned cache name (saraswati-library-v4). At fetch time it uses a network-first strategy — try the network for fresh content, fall back to the cache when offline — while Google Fonts are cached cache-first for speed. An activate handler deletes stale caches so upgrades stay clean.

sw.js — Service Worker (network-first)
const CACHE_NAME = 'saraswati-library-v4';
const ASSETS = [
    './', './css/variables.css', './css/main.css',
    './css/animations.css', './css/components.css',
    './css/pages.css', './css/responsive.css'
];

self.addEventListener('install', (e) => {
    e.waitUntil(
        caches.open(CACHE_NAME).then(cache => cache.addAll(ASSETS))
              .then(() => self.skipWaiting())
    );
});

self.addEventListener('activate', (e) => {
    e.waitUntil(
        caches.keys().then(keys => Promise.all(
            keys.filter(k => k !== CACHE_NAME).map(k => caches.delete(k))
        )).then(() => self.clients.claim())
    );
});

self.addEventListener('fetch', (e) => {
    if (e.request.method !== 'GET') return;

    // Cache-first for Google Fonts
    if (e.request.url.includes('fonts.googleapis.com') ||
        e.request.url.includes('fonts.gstatic.com')) {
        e.respondWith(
            caches.match(e.request).then(r => r || fetch(e.request).then(resp => {
                const clone = resp.clone();
                caches.open(CACHE_NAME).then(cache => cache.put(e.request, clone));
                return resp;
            }))
        );
        return;
    }

    // Network-first for everything else
    e.respondWith(
        fetch(e.request).then(resp => {
            if (resp && resp.ok) {
                const clone = resp.clone();
                caches.open(CACHE_NAME).then(cache => cache.put(e.request, clone));
            }
            return resp;
        }).catch(() =>
            caches.match(e.request).then(r => r || caches.match('./'))
        )
    );
});

7.3 Deployment (Vercel)

Because the whole application is static, it is deployed with the @vercel/static builder. vercel.json pins two important cache headers: sw.js is served with must-revalidate so service-worker updates propagate, while /assets/* is marked immutable for a year so cached images and PDFs load instantly. During development the app is served locally by a small Express server (server.js); the frontend itself is pure static and needs no server.

8. Conclusion

The frontend development of the Library Management System for Shree Saraswati Secondary School was a comprehensive learning experience that covered modern web development technologies and practices.

The project successfully delivered a responsive, user-friendly single page application and a powerful admin panel. The public interface provides students and teachers with a searchable catalog of 100+ books, a digital library for PDF access, borrow request management, and real-time notifications. The admin panel empowers librarians and administrators to manage books, users, reports, settings, and audit logs without any technical expertise.

Throughout the development process, several challenges were encountered and overcome. Building a custom hash-based SPA router from scratch required understanding URL fragment parsing, dynamic parameter extraction, and route guard patterns. Implementing the CSS custom properties theming system involved defining over 60 design tokens and ensuring the dark theme redefined each one correctly. Managing global state across 30+ pages without a framework required a disciplined singleton pattern with clear data flow conventions.

The decision to avoid React, Vue, or Angular proved valuable for this project. Without a build step, every file is readable and editable with a basic text editor. Without a package manager for the frontend, there are no dependency conflicts or version mismatches. The entire frontend is about 35 JavaScript source files totaling roughly 8,000 lines — small enough for a single developer to understand completely.

The dual-backend architecture (Supabase for production, localStorage for demo/offline) was a key design decision. It means the application works even when the Supabase connection is lost, and it allows demonstration of the full functionality without requiring a live database connection.

This project has significantly enhanced my understanding of modern frontend development. I gained practical experience with vanilla JavaScript SPA architecture, CSS custom properties theming, service worker caching, Supabase integration, and responsive design principles. These skills will be valuable in my future career as a software developer.

The Library Management System is now ready for deployment and will serve Shree Saraswati Secondary School effectively, improving their library operations and providing students with digital access to educational resources.
